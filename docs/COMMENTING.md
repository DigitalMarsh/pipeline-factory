# Pipeline Factory 注释规范

本文档约束 Pipeline Factory 的商业化工程注释写法，目标是让维护者理解模块边界、业务不变量和失败处理方式，而不是把代码逐行翻译成自然语言。

## 注释分层

### 模块职责

每个 TypeScript、Vue、CSS 和 Shell 模块都应在文件顶部说明：

- 模块解决的问题和所属层次。
- 它依赖的边界或持有的状态。
- 维护者需要特别注意的业务约束。

模块职责注释应在代码结构变化时同步更新。

### 公共契约

导出的 type、interface、class、function、常量和对外方法使用 TSDoc 或等价注释说明：

- 业务用途，而不是重复名称。
- 关键参数、返回值和副作用。
- 可见的状态转换、错误条件和一致性要求。
- 不可变快照、权限、路径安全或并发限制等不变量。

API 术语、状态名、协议名、类名和字段名保留 English，例如 `PlanRevision`、`SSE`、`PROJECT_ARCHIVED` 和 `Worktree`。

### 复杂逻辑

对状态机、并发、重试、事件回放、快照冻结、路径校验、进程管理和安全策略，在对应逻辑块前解释“为什么这样做”。

行注释只用于补充不明显的决策或防止误改的约束，不解释显而易见的赋值、条件和模板绑定。

## 各类文件要求

- Domain：说明领域不变量、状态转换、持久化事实和适配器边界。
- API：说明路由用途、Project 校验、错误映射、异步任务和 SSE 生命周期。
- Web：说明响应式状态来源、用户交互流程、乐观更新、定位和重连策略。
- Tests：说明业务场景、fixture 设计、边界条件和回归目的；不为每条断言重复注释。
- Shell：说明 PID 文件、健康检查、日志路径、进程树和防误杀逻辑。
- CSS：按布局区域说明视觉层级和响应式约束，避免逐条解释选择器。
- JSON：保持标准 JSON 合法，不添加 `//` 或 `/* */`；字段语义在 README、配置类型或本规范中说明。

## 禁止事项

- 不写与代码逐字重复的注释，例如“递增计数器”紧邻 `count += 1`。
- 不描述已经失效的实现，不在行为变化后保留过期结论。
- 不在注释中写入 API Key、Token、Cookie、个人路径等敏感信息。
- 不用注释掩盖过长函数、隐式副作用或缺少类型约束的问题。
- 不为了补注释进行无关格式化、重命名或业务重构。

## 评审清单

- 新文件是否说明模块职责和边界？
- 公共类型、服务和入口方法是否说明用途、输入、输出和失败条件？
- 状态机、并发、快照、重试、事件流和安全逻辑是否解释设计意图？
- 测试是否说明场景，而不是只罗列断言？
- 注释是否使用中文表达，且保留准确的 API 术语？
- 注释是否仍与当前实现一致？
- 是否避免修改严格 JSON、生成文件和无关代码？
