好，计划模板是整个链路的"契约"——探索线程的输出、执行线程的输入、状态层的解析对象，都靠它对齐。下面是我设计的模板，附带字段说明和一个完整示例。

## 设计原则

1. **零追问**：执行线程（lua）拿到计划后不需要再回探索线程问问题，直接能动手
2. **精确到文件**：改动清单必须落到具体文件，不能只说"修改用户模块"
3. **可验收**：每个计划有明确的完成判定标准
4. **可解析**：元数据区用结构化格式，状态层能自动提取 task_id、deps、涉及文件等

## 字段说明

| 字段             | 谁来填   | 用途                                                         |
| ---------------- | -------- | ------------------------------------------------------------ |
| `task_id`        | 探索线程 | 全局唯一标识，状态层主键                                     |
| `title`          | 探索线程 | 看板展示、快速识别                                           |
| `module`         | 探索线程 | 按模块分组、冲突检测辅助                                     |
| `estimate`       | 探索线程 | 调度器分配时参考（大任务给更稳定的worker）                   |
| `deps`           | 探索线程 | 调度器只分发依赖已完成的任务                                 |
| `affected_files` | 探索线程 | **冲突检测核心**：两个 pending 任务如果改同一文件，调度器串行化执行 |
| `status`         | 状态层   | 探索线程不维护，生成时固定 `pending`                         |
| 正文各节         | 探索线程 | 执行线程的直接输入                                           |

## 关键设计点

**1. `affected_files` 是冲突检测的基础**

调度器在分配任务前检查：如果某个 worker 正在执行的任务和待分配任务有文件交集，则不分配给该 worker，等它空闲。这能大幅减少合并冲突。

**2. "改动清单"按文件组织，而不是按步骤组织**

执行线程的工作方式是逐文件修改，按文件组织让它可以直接对照执行。每个文件下面写清楚"改什么、怎么改、关键逻辑"，但不要写完整代码（那是执行线程的活），写**设计决策和接口签名**即可。

**3. "验收标准"用 checkbox 列表**

执行线程完成后可以逐项自检，你合并 review 时也可以直接对照。全部打勾才算 `done`。

**4. "执行提示"是给 lua 模型的拐杖**

lua 模型性价比高但可能不熟悉项目细节，这里告诉它测试命令、参考文件、环境变量，减少它自己摸索的时间和出错率。

## 使用方式

**探索线程侧**：每次讨论完一个功能，按这个模板输出一份计划，写入状态层（状态层解析 frontmatter 提取元数据，正文存为 plan_content）。

**执行线程侧**：从状态层取到任务后，把整个计划内容作为 system prompt 或首条消息发给 codex，让它在 worktree 中执行。执行完成后对照验收标准自检，然后更新状态为 `done` 或 `failed`。

**你 review 时**：只看 `title` + `改动清单` + `验收标准` 就能判断计划是否正确，不需要读全文。

------

这个模板你觉得怎么样？有几个可以调整的点：

1. **粒度**：当前模板适合"一个接口/一个功能点"级别的计划，如果你的功能更大，可能需要拆分子任务
2. **格式**：frontmatter 用 YAML，正文用 Markdown，codex 对这种格式理解最好；如果你偏好纯 JSON 也可以改
3. **字段增减**：比如要不要加 `rollback_plan`（回滚方案）、`test_data`（测试数据准备）等

你确认后，下一步可以做**状态层的数据结构和调度脚本**，或者先拿一个真实功能试跑一遍这个模板看看顺不顺手。
