## 一、数据、数量与统计口径

### 1. C 模式的消息、状态与活动数量混用了口径

- 文档位置：第 39 行，§0 界面清单。
- 原文：“2 类消息 ×6 状态 +3 种活动行”。
- 问题：用户消息提交时固定为 `COMPLETED`，助手消息才经历多种状态；活动附注共用一个模板，标签函数有 4 条返回路径，不能直接计为 3 种活动行。
- 建议：分别描述角色、状态和活动呈现，避免使用乘法表示所有角色都具有全部状态。
- 依据：[用户消息写入](../code/packages/domain/src/agent/project-execution-thread.ts)（169–171 行）、[活动标签及模板](../code/apps/web/src/components/ProjectExecutionThreadPanel.vue)（237–244、357–358 行）。

### 2. ④“扩到 12 个”没有对应的当前计数

- 文档位置：第 1803 行，§7 清理记录。
- 原文：“扩到 12 个”。
- 问题：`ProviderActivityKind` 共 19 个，其中 `RUNTIME_KINDS` 有 9 个；§0.1 列出的④消息类型是 10 个。这些统计对象均不对应 12。
- 建议：明确统计的是中立活动类别还是呈现消息类型，再订正数字。
- 依据：[Provider 活动词表](../code/packages/domain/src/model/provider-activity.ts)（41–64、90–100 行）。

### 3. Claude 执行线程统计混用了后端与模型名称

- 文档位置：第 1640 行，§5.4 快照之后补齐的证据。
- 原文：“4 条 `claude-agent-sdk` 的执行线程”，其中包含一条 backend 记为 Codex、model 为 `claude-opus-5` 的历史行。
- 问题：只读查询当前运行库，`telemetry.backend=claude-agent-sdk` 为 3 条；另外一条是 `backend=codex-app-server`、`model=claude-opus-5`。模型名称与后端标识不是同一个统计口径。
- 判断边界：这不证明第四条实际走了 Codex，旧端点指纹可能有误；也不能只凭模型名证明它实际走了 Claude。
- 建议：分别写明“记录后端为 Claude 的 3 条”和“疑似旧指纹错误的 1 条”，补充第四条实际路由的证据。
- 依据：`code/pipeline-factory.sqlite` 的 `execution_threads.telemetry_json` 只读查询；[路由端点指纹实现](../code/apps/api/src/runtime/model-gateway.ts)（123–142 行）。

### 4. “分三类看”实际列出了四类

- 文档位置：第 1896 行，§8.2 标题。
- 问题：下文有 A、B、C、D 四类。
- 建议：改为“分四类看”。

## 二、与实现不符或流程说明不完整

### 5. `conversationId` 恒为 `run.id` 的范围过大

- 文档位置：第 145 行，§0.1 会话说明。
- 问题：探索请求使用 `ExplorerPlan.id`，项目执行线程使用线程 ID。
- 建议：将该结论限定为 Run 执行路径，不作为所有 Provider 会话的通用定义。
- 依据：[探索请求](../code/packages/domain/src/explorer/thread-service.ts)（327、634 行）、[项目执行请求](../code/packages/domain/src/agent/project-execution-thread.ts)（407 行）。

### 6. Factory“不直接调模型的 API”不是整个实现的事实

- 文档位置：第 138 行，§0.1 角色定义。
- 问题：路由仍支持 `openai-responses`；`OpenAIModelGateway` 在 Factory 进程内通过 `fetch` 调用模型 API。
- 建议：限定为本文重点讨论的 Codex App Server／Claude Agent SDK 两条路径，或补充直接 API 后端的例外。
- 依据：[后端构造](../code/apps/api/src/runtime/model-gateway.ts)（250–256 行）、[API 请求实现](../code/packages/domain/src/model/gateway-openai.ts)（59–66 行）。

### 7. 消费方“永远看不到 Provider 原生词”过于绝对

- 文档位置：第 1483 行，§5.1 分层表。
- 原文：“只有本文件知道 itemType 的含义”“消费方永远看不到 Provider 原生词”。
- 问题：历史数据读取仍按原生 `itemType` 兜底分类，未知类型也会显示原生名称。
- 建议：区分新事件的中立分类路径与历史兼容路径。
- 依据：[探索侧历史兜底](../code/packages/domain/src/explorer/explorer-activity.ts)（521–525 行）、[执行侧历史兜底](../code/apps/web/src/utils/executionStream.ts)（1096、1168 行）；文档自身第 344 行也说明未知类型标签直接显示原生 `itemType`。

### 8. Plan 恢复边的“变更提案”标签不准确

- 文档位置：第 639–640、653–655 行，§1.3 D。
- 原文：`VERIFYING／MERGE_READY → IN_PROGRESS` 标为“对账／变更提案”。
- 问题：变更提案创建后进入 `NEEDS_PLAN_CHANGE`，批准后进入 `ENQUEUED`；`MERGE_READY → IN_PROGRESS` 还有追加要求续跑的实际写入点。
- 建议：按实际写入原因标注转换边，不把变更提案描述成直接返回 `IN_PROGRESS`。
- 依据：[创建及批准变更提案](../code/packages/domain/src/run/change-proposal.ts)（59–64、122–133 行）、[追加要求续跑](../code/packages/domain/src/run/scheduler.ts)（558–560 行）。

### 9. Plan 主流程图遗漏验证阻塞的明确业务边

- 文档位置：第 626–644 行，§1.3 D 流程图。
- 问题：未画出 `VERIFYING → BLOCKED`。后文通用重置规则虽然覆盖该转换，但验证预算用尽或无修复器时，这是明确的主业务路径。
- 建议：在主图直接补充验证失败且无法继续修复时进入 `BLOCKED` 的边。
- 依据：[验证失败处理](../code/packages/domain/src/run/verification.ts)（82–108、123 行）。

### 10. 启动恢复“一律转 RECOVERING”遗漏需要对账的分支

- 文档位置：第 1068 行，启动恢复说明。
- 问题：存在 `UNKNOWN／NEEDS_RECONCILIATION` 工具调用时，Loop 优先进入 `NEEDS_RECONCILIATION`，而非 `RECOVERING`。
- 建议：写明优先判断未知工具副作用，并分别说明 Loop 状态与关联 Run 的恢复状态。
- 依据：[恢复分支](../code/packages/domain/src/run/recovery-coordinator.ts)（35–49 行）、[关联 Run 恢复](../code/packages/domain/src/run/recovery-coordinator.ts)（116–125 行）。

### 12. 事件副本的合并边界与 journal 并不完全相同

- 文档位置：第 1991、2003 行，§9.1–§9.2。
- 原文：事件副本按序号相邻合并，与上两行“一一对应”；合并规则与上表段边界“逐字相同”。
- 问题：事件副本除序号相邻外，还检查 `modelStep／providerItemId`，但没有检查 `phase`；journal 已检查 `phase`。因此不同表的分组边界并不逐字相同。
- 建议：分别列出各表真实分组条件，收窄“一一对应”的保证。文本拼接可能保留文字，但这不能证明分段及元数据也完全一致。
- 依据：[事件副本分组](../code/packages/domain/src/store/sqlite-store.ts)（2950–2962 行）、[journal 分组](../code/packages/domain/src/store/sqlite-store.ts)（3041–3052 行）。

### 13. C 模式活动附注的来源与分类不准确
