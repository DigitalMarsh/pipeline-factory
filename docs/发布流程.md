# 发布流程

本文是 Pipeline Factory 的**唯一发布手册**：从定版本到 npm / GitHub 双通道发布，再到验证与回滚。
所有命令除非特别说明，都在仓库根目录执行。

发布只有两条产物，都是同一个源码树构建出来的：

| 产物                                       | 构建命令            | 去向            | 用途                                            |
| ------------------------------------------ | ------------------- | --------------- | ----------------------------------------------- |
| npm 单包 `pipeline-factory-X.Y.Z.tgz`      | `pnpm pack:npm`     | npm registry    | `npm install -g pipeline-factory`（**主通道**） |
| 离线发布物 `pipeline-factory-X.Y.Z.tar.gz` | `pnpm pack:release` | GitHub Releases | 无外网/受限环境：`./install.sh`                 |

**发布原则**

1. **一次发布只对应一个提交**。版本号、CHANGELOG、tag 指向同一个 commit。
2. **门禁全绿才发**。`pnpm verify` 失败时不打 tag、不发布。
3. **npm 包与发布物都不含 Claude Agent SDK**（体积与许可原因）；SDK 由目标机器提供。
4. **数据库结构只升不降**。新版本创建的库，旧版本会拒绝打开（`SCHEMA_TOO_NEW`），涉及 schema 变更时必须在 CHANGELOG 写明不可回退。
5. **凭据不进仓库、不进命令历史**。npm 2FA 验证码在交互终端里输入；token 只用于 CI，用完立即撤销。

---

## 0. 一页清单

```text
[ ] 1. 定版本：四个 package.json 同步
[ ] 2. 写 CHANGELOG
[ ] 3. pnpm verify 全绿
[ ] 4. pnpm pack:release + pnpm pack:npm
[ ] 5. 本地冒烟：临时前缀安装 → start/status/stop → update
[ ] 6. 提交 + push main
[ ] 7. 打 tag vX.Y.Z + push tag
[ ] 8. gh release create（上传 tar.gz）
[ ] 9. npm publish（交互终端输入 OTP）
[ ] 10. 发布后验证：npm view / 干净安装 / update
```

---

## 1. 准备

- 在 `main` 分支，工作区干净：

  ```bash
  git status --porcelain
  ```

  只允许出现你明确不提交的个人目录（例如未跟踪的本地资料）；有代码改动先提交或丢弃。

- 工具就绪：Node.js ≥ 22.5、pnpm、`gh` 已登录、npm 已登录。

  ```bash
  node -v && pnpm -v && gh auth status && npm whoami
  ```

- **npm 2FA**：本账号发布时需要一次性验证码（OTP）。验证码来自启用 2FA 时绑定的验证器 App，
  30 秒刷新。**在自己的交互终端里执行 `npm publish`**，npm 会在提示符里要验证码；
  不要用 `--otp=<code>` 写进脚本，也不要把 token 拼进命令（既会过期，也会泄漏到历史/日志）。

---

## 2. 定版本

版本号以 `apps/api/package.json` 为**构建来源**（`pack:release` 与 `pack:npm` 都读它），
但四个包必须保持一致，避免调试时版本互相矛盾：

```bash
# 把 X.Y.Z 换成目标版本
for f in apps/api apps/web packages/core packages/contracts; do
  node -e "const fs=require('fs');const p='$f/package.json';const j=JSON.parse(fs.readFileSync(p));j.version='X.Y.Z';fs.writeFileSync(p,JSON.stringify(j,null,2)+'\n')"
done
```

选版本号：

- 只修 bug / 文档 → patch（0.2.2 → 0.2.3）
- 新增向后兼容能力（如新增安装方式） → minor（0.2.x → 0.3.0）
- 破坏性变更、数据库 schema 变更、配置字段不兼容 → major（0.x 阶段也要在 CHANGELOG 明说）

---

## 3. 写 CHANGELOG

在 `CHANGELOG.md` 顶部新增一节，格式与既有条目一致：

```markdown
## YYYY-MM-DD — vX.Y.Z：一句话标题

- 改了什么（动机 → 影响面）。
- 用户需要做什么（升级命令、配置变更、不可回退提示）。

验证：`pnpm verify` 全绿；打包/安装/升级链路实测。
```

CHANGELOG 记录的是**用户可感知的变化与验证方式**，不写内部琐事。

---

## 4. 门禁

```bash
cd code && pnpm verify
```

必须全绿。`scripts/test-baseline.json` 的期望状态是**空**；新失败不允许被登记成豁免。

门禁包含：contracts/core 构建 → 三个包 typecheck → lint → prettier → 三个包测试 → 循环依赖 →
悬空引用检查。

---

## 5. 构建

```bash
cd code
pnpm pack:release   # → release/pipeline-factory-X.Y.Z/ 与 release/pipeline-factory-X.Y.Z.tar.gz
pnpm pack:npm       # → release/pipeline-factory-X.Y.Z.tgz（同时生成 npm-package/ 打包目录）
```

构建后自检：

```bash
# npm 包：10 个文件、约 1.5MB、只含运行时
tar -tzf code/release/pipeline-factory-X.Y.Z.tgz | sort

# 发布物：不含 Claude SDK、不含 node_modules
tar -tzf code/release/pipeline-factory-X.Y.Z.tar.gz | grep -E "@anthropic|node_modules" || echo "clean"

# 版本与依赖
tar -xzOf code/release/pipeline-factory-X.Y.Z.tgz package/package.json | head -20
```

`release/` 与 `npm-package/` 都是生成目录，已在 `.gitignore` 中，**不要提交**。

---

## 6. 本地冒烟（发布前的最后一道闸）

用临时前缀与临时数据目录，完整走一遍用户路径：

```bash
rm -rf /tmp/pf-prefix /tmp/pf-home
npm install -g --prefix /tmp/pf-prefix code/release/pipeline-factory-X.Y.Z.tgz

# 首次启动会自动生成 ~/.pipeline-factory 配置；这里用临时目录隔离
PIPELINE_HOME=/tmp/pf-home /tmp/pf-prefix/bin/pipeline start
PIPELINE_HOME=/tmp/pf-home /tmp/pf-prefix/bin/pipeline status
curl -s http://127.0.0.1:4310/health
PIPELINE_HOME=/tmp/pf-home /tmp/pf-prefix/bin/pipeline stop
```

检查点：

- `pipeline version` 输出 `X.Y.Z`；
- `/health` 的 `appVersion` 是 `X.Y.Z`，`instanceId` 非空（说明启动探针认的是自己的实例）；
- 首页 `curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:4310/` 返回 200；
- 端口被其他实例占用时，`pipeline start` 应在约 0.3 秒内报 `STARTUP_PROCESS_EXITED`，
  而不是误报成功或等满 30 秒；
- 升级路径：

  ```bash
  PIPELINE_HOME=/tmp/pf-home /tmp/pf-prefix/bin/pipeline update --file code/release/pipeline-factory-X.Y.Z.tgz
  ```

  应打印 `npm install -g --prefix /tmp/pf-prefix ...`，随后自动重启且 `status` 版本正确。

`/tmp` 下若 4310 被占用，先改临时配置里的 `server.port` 再启动。

## 7. 提交、推送、打 tag

```bash
git add CHANGELOG.md docs/... apps/... packages/... （按实际改动）
git commit -m "chore(release): vX.Y.Z"
git push origin main

git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
```

- 提交前 pre-commit 钩子会自动 prettier；钩子失败就修好再提交。
- tag 必须在**最终提交**上打；一旦 tag 推送后才发现漏改动，只能发新的 patch 版本。

---

## 8. GitHub Release（离线发布物）

```bash
gh release create vX.Y.Z \
  --title "vX.Y.Z — 一句话标题" \
  --notes-file /tmp/release-notes.md \
  code/release/pipeline-factory-X.Y.Z.tar.gz
```

- **不要**传 `--target` 的短 SHA（GitHub 会对不完整的 commit SHA 返回 422）；tag 已在第 7 步推送，
  不需要 `--target`。
- npm 包**不必**上传到 GitHub（npm 已是权威来源）；如需离线归档可以一起传。
- 发布后核对：

  ```bash
  gh release view vX.Y.Z --json tagName,assets
  ```

- Release notes 建议写：本版变化、升级命令、是否需要改配置、是否可回退。

---

## 9. npm 发布（主通道）

```bash
cd code/npm-package
npm publish
```

- 在**交互终端**执行；npm 提示 `Enter OTP:` 时输入验证器当前的 6 位码。
- 若提示需要浏览器确认安全密钥，按浏览器流程完成即可。
- 不要把 OTP 或 token 写进脚本/仓库；也不要 `npm publish --//registry.npmjs.org/:_authToken=...`
  把 token 拼在命令行里。
- 发布成功后立刻验证：

  ```bash
  npm view pipeline-factory version        # → X.Y.Z
  npm view pipeline-factory dist-tags      # latest → X.Y.Z
  ```

**关于 `0.0.0-stage`**：npm 的 staged publishing 机制会在包上留下一个
`0.0.0-stage` 占位版本（描述为 "Temporary package placeholder for staged publishing"）。
它不是本包的内容，`dist-tags.latest` 仍指向真实版本，`npm install` 不受影响。
npm 网页的版本下拉里可能先看到它，属正常现象；确认无影响即可忽略。
如需清理，发布后 72 小时内可以：

```bash
npm unpublish pipeline-factory@0.0.0-stage
```

---

## 10. 发布后验证（用户视角）

在一台干净机器或一个全新目录：

```bash
npm install -g pipeline-factory
pipeline start
pipeline status
```

- 首次启动会生成 `~/.pipeline-factory/config/pipeline-factory.config.json`；
- 确认 `project.root` 指向真实代码仓库后再跑业务；
- 已有旧版本的用户：`pipeline update` 应升级到 `X.Y.Z`（npm 布局下执行
  `npm install -g --prefix <当前前缀> pipeline-factory@latest`）。

---

## 11. 回滚

| 通道        | 动作                                                                              | 限制                                                                       |
| ----------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| npm         | `npm unpublish pipeline-factory@X.Y.Z`                                            | 发布后 72 小时内；已被依赖的版本可能拒绝                                   |
| npm（推荐） | `npm deprecate pipeline-factory@X.Y.Z "有问题，请安装 X.Y.(Z-1)"`                 | 任意时间；保留可下载                                                       |
| GitHub      | `gh release delete vX.Y.Z --yes` + `git push --delete origin vX.Y.Z`              | 删除后 `pipeline update` 会退回上一版 release                              |
| 本地用户    | `pipeline update --file pipeline-factory-X.Y.(Z-1).tar.gz`（离线）或 npm 指定版本 | 数据 schema 不降级；涉及 schema 变更时旧版本会拒绝启动（`SCHEMA_TOO_NEW`） |

涉及数据库 schema 的版本，回滚前必须先 `pipeline stop` 并备份 `~/.pipeline-factory/var/`。

## 12. 常见问题

| 现象                                      | 原因 / 处理                                                                            |
| ----------------------------------------- | -------------------------------------------------------------------------------------- |
| `EOTP` 反复失败                           | 验证码 30 秒过期；在自己的交互终端执行 `npm publish`，按提示当场输入                   |
| 发布后网页仍显示旧版本                    | npm 网页缓存；以 `npm view pipeline-factory dist-tags` 为准，强制刷新页面              |
| 网页显示 `0.0.0-stage`                    | npm staged publishing 占位版本；`latest` 指向真实版本，安装不受影响                    |
| `npm install -g` 后 `pipeline` 不是新版本 | 装到了另一个 npm 前缀；用 `npm root -g` / `which pipeline` 核对，或显式 `--prefix`     |
| `pipeline update` 升级后仍是旧版本        | 升级前缀与安装前缀不一致；`npm install -g --prefix <安装前缀> pipeline-factory@latest` |
| `SCHEMA_TOO_NEW`                          | 用旧程序打开了新库；升级到对应版本，不要降级                                           |
| `CLAUDE_AGENT_SDK_UNAVAILABLE`            | 目标机没装 SDK；见 `docs/INSTALL.md` 第 4 节（或配置 `sdkPath`）                       |
| `gh release create` 返回 422              | 用了 `--target` 的短 SHA；去掉 `--target`，确保 tag 已推送                             |
| npm 包漏文件                              | 检查 `build-npm.mjs` 的 `files` 字段与 `npm pack --dry-run` 输出                       |

---

## 13. 发布记录

每次发布在 CHANGELOG 对应条目里留下：版本、日期、验证方式、是否有不可回退变更。
GitHub Releases 与 npm 的版本号必须一致。
